These NEW evolution/supply requirements take precedence over historical baseline behavior. Every JSON in tests/fixtures/evolution_supply is NEW. The initial run is a documented transformation of a historical baseline-generated seed-42 DTO in a disposable scratch copy. ## Fixture packet and helper API

- run_v2.json: map with `initial`, one new standard-doctrine nonstreamed reference DTO. Absence of `world` is deliberate, not a placeholder streamed world.
- game_save_v2.json: `empty` (revision0, next serial1, settled0, checkpoint null) and `started` (revision1, next serial2, settled0, exact initial checkpoint).
- progression_views.json: `missing`, `blocked`, `ready`, `evolved`; rendering-only views. progression_source_offers.json contains their corresponding independently authored authoritative offer samples. These samples are not full combat snapshots.
- `blocked` is a legal prospective fourth passive slot choice while movement is still missing: it warns that choosing armor will block the target. Current target status remains `collecting`, because the slot has not yet been consumed. After such selection the production evaluator must return `blocked`/`passive_slots`; no fixture pretends both states exist at once.
- supply_views.json: `affordable` (40), `insufficient` (39), `owned` (mobile already unlocked), `full` (9 bandages), each with all three rows and actual loadout options. These are rendering examples, not save authorities.
- attack_events.json: `blade`, `wing_cut`, `crossfire`, each `{events,reservations}`. Reservations are cast-time records; events cover their scheduled/executed lifecycle. Not replay-derived combat proof.
- content_identity_basis.json and provenance.json: explicit fixture identity and claim limits.

Recovered helper method names remain: `run_state(case_id="initial")`, `game_save(case_id="initial")`, `progression_view(case_id)`, `supply_view(case_id)`, `attack_events(case_id)`, `make_run(chapter,seed,config)`, `validate_checkpoint(value)`. NEW case routing is now real: game_save `initial` aliases `empty`; progression `last_slot_warning` aliases `blocked`. Unknown case returns empty instead of silently substituting another case. NEW `progression_source_offer(case_id)` and `attack_reservations(case_id)` expose copies. Every read returns an independent deep copy. Test make_run fills run identity/config/seed only and is not doctrine/chapter combat implementation.

## Common envelope and normalization

Persistence/view DTOs are JSON-safe Dictionaries/Arrays/scalars; positions/directions are numeric two-arrays and rectangles four-arrays. No saved Nodes, Resources, Callable, Vector2 or Rect2. Pure internal world query methods retain their recovered Vector2/Rect2 API. Failure envelope is `{ok:false,error_code:String}` with optional diagnostics. Absence of a required field is an error; no guessed empty field may be inserted merely to pass validation.

Integral JSON floats normalize only after finite, nonnegative, integral and maximum checks. Economy and ordinary persistent counters cap at 2147483647. Signed `final_started_tick=-1` is the sole unstarted sentinel. RNG states are decimal strings; world address strings and exact codec limits have separate contracts. `snapshot`, views, catalog rows, candidates and receipts return deep copies.

Any further persistent field must be enumerated in this contract before introduction.

Player retains id, position, velocity, facing, radius, hp, max_hp, invulnerable_until, xp, level, attack_ready_ticks. Stats retain kills, damage_dealt, minibosses_defeated. No fabricated empty enemy catalog: the initial reference includes the historical catalog and is explicitly not a completed new combat definition set.

`run_config={run_id,run_serial,doctrine_id,target_evolution_id,prepared_supply}` is immutable after start, matching the complete recovered SupplyService factory call. Content identity is authoritative at RunState content_revision/rules.content_fingerprint, not an invented mandatory config field. IDs: run_id `<career_id>:<serial>`, cast_id `<run_id>:attack:<attack_seq>`, attack_id `<cast_id>:<stage_index>`, event_id `<run_id>:<event_seq>`. Offer IDs use `<run_id>:offer:<offer_seq>`, and option IDs use `equipment:<item>`, `passive:<item>`, `evolution:<evolution>`; focus is a semantic ID. Because option IDs repeat across levels, accepting a selection MUST bind the complete offer_id + run_id + current authority/view generation, not option_id alone. A regression test must replay an old same-named option after next-offer promotion and after authority replacement, reject it, and leave clocks/RNG/offer/seals unchanged.

Equipment and passives each have four slots, levels1–5. Evolutions map base item to one evolution and consume no extra slot. `tactical_seals + evolutions.size() == number of unique claimed real boss reward IDs == stats.minibosses_defeated`, maximum5. Final threat has no seal/reward. Pending offers have ONLY `{offer_id,source,level_ordinal}`. Source is `level` or `boss`; level_ordinal records player level at enqueue. The active `state.upgrade_offer` stores exactly materialized option identities/levels and selected_option_id, not another mutable RNG result.

`ProgressionView.build` returns `{view_revision,slots,target,evolutions,active_offer}`. Slots keys are singular `equipment` and `passive`, each `{used,max}` as consumed by recovered GameUI. Each evolution has evolution_id, base_item_id, name, description, status, can_evolve, requirements, effect_delta, tradeoff_text. Status enum: unavailable/collecting/blocked/ready/evolved. Each requirement has kind, item_id, name, current, required, met, blocked_reason. Kinds: equipment/passive/seal. Option DTO adds option_id, item_id, kind, level, next_level, can_select, blocked_reason, slot_warning; nonapplicable presentation text may be the authored empty string.

The authoritative `state.upgrade_offer` maps to derived `view.active_offer` by deep copy. Same offer_id, option IDs, current/next levels and selected_option_id; view may add derived description/effect/requirements, but never change identity. Replacing/mutating a UI copy does not modify RunState. A controller view binding includes authority generation, run ID and store revision outside this view DTO; stale detail cannot resume/choose/buy/start merely because offer_id matches.

Growth RNG initializes from `(seed ^ 0x5EED1203) & 0x7fffffff` using pinned Godot4.6.3; store RNG state decimal string. Combat RNG remains separate. Stable IDs sorted before random sampling. Evaluate/view/restore do not consume RNG. Ready evolutions precede target-priority even-level upgrades, then unique random legal choices. Target priority: missing passive, missing weapon, weapon to5, passive to3. One/two choices remain one/two; zero choices heal10% max HP without modal or currency.

Core APIs: new_run(chapter,seed,run_config) returns state or failure; step(state,move:Vector2,commands:Array[Dictionary]) mutates only Core-owned state; snapshot(state) copies; restore(snapshot,hydrated_deltas={}) returns `{ok:true,state}` or failure; choose_upgrade(state,offer_id,option_id) returns result/events and never writes storage. set_pause, set_offer_focus and abandon_run are semantic operations; abandoned is a distinct terminal phase. EvolutionCatalog.validate/evaluate, UpgradeCatalog.candidates, GrowthOfferService.materialize(state,descriptor)->{ok,offer,next_rng_state}, ProgressionView.build are the single authorities. UI, economy and world components must not duplicate these rules.

## Attack reservation and presentation schema

Player reservation fields: attack_id, cast_id, base_item_id, evolution_id, attack_started_tick, execute_tick, stage_index, stage_count, origin_binding (`fixed`/`player`), origin, direction, shape, radius, arc_degrees, damage, hit_entity_ids, pose_tag. Applicable line/projectile geometry also carries its real length/width/projectile ID rather than guessed values. Adding a required field requires corresponding contract and test coverage. Maximum64 player reservations, separate bounded enemy reservations. Reserve an entire two-stage cast or none; sort due work by (execute_tick,attack_id). A target can be hit once per attack_id, twice across two distinct stages. Death/drop accounting remains once.

`player_attack` envelope: `{event_id,type:"player_attack",tick,payload}`. Required payload fields are cast_id, attack_id, base_item_id, evolution_id (empty for base weapon), origin, direction, attack_started_tick, execute_tick, stage_index, stage_count, phase (`scheduled`/`executed`), pose_tag, geometry. Geometry contains actual shape/origin/direction and applicable dimensions. The R0 payload also preserves reservation flat fields for inspection; shape/radius/arc/origin remain required in saved crossfire reservations because exact VFX reconstructs geometry from them. Event sequence is monotonically increasing; replay never creates currency.

Hand values with no damage/range/cooldown passives: blade Lv1 damage12/radius54/arc150 immediate at100. Blade Lv5 damage=12+4*6=36; wing cut .75*36=27 and1*36=36 at100/112, radius88/arc110/cooldown48. Direction remains[1,0]; second execution origin becomes[12,0] in this example, its cast-time player-bound origin was[0,0]. Cannon Lv5 damage=24+4*10=64; each crossfire .7*64=44.8 at136/166, radius56/cooldown168/acquisition456; locked target[100,0] and perpendicular[0,1] give[100,-24]/[100,24]. Target movement/death cannot change these points. Existing cooldown ready tick survives evolution. All six base weapons must later use this event contract.

Projectile persistent schema for later real-combat validation: id, item_id, attack_id, cast_id, position, velocity, damage, splash_radius, remaining_distance, radius. Projectile identity is linked to its original cast/stage and cannot be regenerated on restore. Saved positions rebase once; velocity/direction never rebase. Launch emits executed player_attack with geometry.shape=projectile, geometry.projectile_id matching id and actual radius. Hits emit damage and optional projectile_impact with projectile_id/attack_id/base_item_id/position/radius; damage alone never starts a soldier slash. No projectile fixture exists at R0; a later fixture must use real Core.

## Compatibility UX and recovery: do not collapse different failures

1. Dev1 profile/settings/unlocks/history are independent of an unplayable legacy run and must remain intact. V1 checkpoint plus backups remain byte-preserved, never played under new rules. No inferred backpay.
2. Supported economy authority with an unsupported checkpoint must offer the explicit user choice: **“기존 전투를 보존하고 새로 출격”**. Never silently delete/reset/discard the checkpoint, never rewrite it to an invented terminal state or settlement, and never make a permanent feature lock the only outcome.
3. This choice requires reading and content-addressed archiving the entire original authority/checkpoint bytes, then verifying archive readback. Validate economy/profile/career/serial high-water/receipts independently. An explicit compatibility migration receipt and/or atomic replacement-run start transition requires validation before implementation. Preserve every verified profile/currency/history/receipt value; advance serial safely, never reset/reuse it. This is NOT implemented or represented as an allowed fixture schema extension in R0. A plain checkpoint=null assignment in a started career is invalid. An archive/hash alone is not user approval or economic validity.
4. Unsupported/future WHOLE authority schema or unvalidated economy cannot be safely split. Preserve read-only, report the exact compatibility issue and await supported recovery; do not create an empty profile, guess credits, discard unknown fields, overwrite with v1 or start over against that authority. Distinguish this from checkpoint-only incompatibility.
5. Transient read_failed/storage errors are retryable observations, not permanent incompatibility. Keep the last verified live authority and pending operation ID; read back current authority/receipt and retry the same ID when safe. A proven pre-replace failure means not applied. Post-replace/readback uncertainty means commit_outcome_unknown, never “not applied”. Hold dependent economic action until reconciled; do not invent permanent locks, mint a new ID, auto-buy/start or endlessly mutate on read errors.
6. No automatic/destructive cleanup of originals, archives, backups or possible world roots in uncertainty. All recovery paths need fault-injected tests and verified preservation before activation.

Never update live Core before GameSave readback.

One explicit dispatcher validate_checkpoint(snapshot) is passed to GameSaveStore. Supported nonstreamed snapshot calls REAL one-argument validation_simulation.restore(snapshot). ## Reviewed error/condition registry

Public failure codes preserve spelling and distinguish category. A component may return a more specific preserved world code below, with diagnostics; no automatic conversion of storage errors to permanent locks.

- Compatibility: unsupported_schema (scope must identify whole authority vs checkpoint), content_mismatch (revision/fingerprint; same scope distinction), unsupported_checkpoint (NEW controller/recovery presentation condition, not yet a stored schema or Store return).
- Invalid state/input: invalid_snapshot, invalid_core_state, invalid_player, invalid_entity, invalid_item, invalid_offer, invalid_option, invalid_offer_queue, invalid_pause_reason, invalid_run_config, invalid_chapter, invalid_initial_equipment, invalid_world_geometry, invalid_game_save, invalid_profile, invalid_loadout. Reject input; keep existing authority.
- Semantic transaction: stale_revision (refresh/readback, no auto resubmit), request_conflict (same ID different payload, reject), active_run (explicit continue/end or reviewed compatibility choice), counter_exhausted, insufficient_funds, already_owned, inventory_full, not_owned.
- Growth requirement conditions, not storage failures: missing_weapon,missing_passive,weapon_level,passive_level,seal_required,equipment_slots,passive_slots,chapter_not_allowed,already_evolved.
- Storage: not_found (absence only; distinct from unreadable), read_failed,write_failed,verify_failed,backup_failed,replace_failed,commit_outcome_unknown. Only last means commit may have replaced authority; reconcile same ID before another transaction.
- World: world_not_ready,outside_working_set,working_set_capacity,handover_capacity,invalid_query,unsupported_radius,invalid_generator,invalid_hydration,invalid_chunk_address,invalid_prop_delta,unknown_prop_slot,unknown_dirty_chunk,delta_stage_required,stale_world_revision,blocked; preserve exact Codec/Store page/root integrity codes rather than remap to empty terrain. world_receipt_invalid/world_receipt_stale are explicit receipt validation failures. Preserve failed/uncertain root candidates for reconciliation; page-store failures never authorize an empty world or checkpoint reset.

`notice_code` describes successful recovered/migrated load, never overrides error semantics. New codes require compatibility validation and updates to consumer handling/tests; UI translations are not validation rules. Compatibility recovery methods and additional world structural fields remain pending implementation and validation, not tacitly implemented APIs.
